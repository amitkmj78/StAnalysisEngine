Architecture — Search & LLM Pipeline

How search feeds the LLM

Every narrative, sentiment summary, and drop alert this app generates about a stock is grounded in real, current text — not just the model's training data. This is the pipeline that gets that text: where it's found, how it's cleaned, and how it reaches the model.

Where results come from

Discovery tries three sources in order, falling through only when one has nothing to offer — this keeps results fast and current without ever depending on a single point of failure.

CrawlSearch — our own crawler no coverage → Brave Search API unconfigured → DuckDuckGo
Why our own crawler comes first: CrawlSearch's results are pre-extracted at crawl time — querying it costs one internal lookup, not a live fetch of the original site. Live sources (Brave, DuckDuckGo) only run when a topic falls outside CrawlSearch's curated coverage.

CrawlSearch — the primary source

A standalone crawler that continuously indexes a curated list of finance and news sites, built and run specifically to feed this pipeline with fresh, on-topic content.

CrawlPolite by construction

Every domain's robots.txt is fetched and honored before anything else — a site that disallows crawling is skipped, never worked around. Per-domain rate limiting respects the site's own Crawl-delay when it's stricter than our default, and 429/503 responses trigger backoff rather than retries.

New pages are found via each domain's sitemap or homepage links; a paginated sitemap index (a pointer to hundreds of sub-sitemaps) is deliberately skipped rather than followed, so the crawl budget goes to real articles, not XML discovery.

ExtractExcerpts, not full articles

Each page is parsed for its actual article text — preferring semantic <article>/ <main> tags, falling back to a paragraph-density heuristic — and capped at roughly 2,000 characters. News writing front-loads the facts, so this is normally the lead paragraphs: enough for LLM context, deliberately short of a full republished copy.

IndexPostgres full-text search

Extracted text lands in a Postgres table with a generated tsvector column (title weighted above body) and a GIN index, ranked by Postgres's built-in ts_rank. A search is a local query against already-crawled data — no network round trip, typically under a few hundred milliseconds.

RetainA rolling window, not an archive

Every crawl cycle purges pages older than the retention window and forgets their URLs from the crawl frontier, so they're eligible to be recrawled fresh if still live upstream. This is a cache of recent content for LLM grounding, not a permanent copy of anyone else's reporting.

Where the LLM actually comes in

Search results reach the model in two distinct passes, not one.

Pass 1 — Summarization (optional, per search)

Raw multi-source results are noisy: near-duplicate headlines across sites, ad copy mixed into extracted text, truncated snippets. When a caller has an LLM in scope, results are run through a summarization prompt first — deduplicate, drop anything promotional, keep concrete facts (numbers, dates, named catalysts), and flag disagreement between sources rather than silently picking one. This step fails open: if the LLM call errors, the raw formatted results are used instead, never a blocked response.

Pass 2 — Analysis (the actual narrative/sentiment call)

The (possibly summarized) search context is handed to the feature that asked for it in the first place — a prediction narrative, a portfolio drop-alert explanation, a sentiment summary for a ticker. That call reasons over real, current text about the stock alongside the quantitative signals it already has, instead of relying on the model's training data alone for anything time-sensitive.

Which model actually answers

Every LLM call above — summarization and analysis alike — goes through the same resilience layer, not a single hardcoded provider that takes the whole pipeline down if it has a bad day.

Groq — default fails → OpenAI — second choice fails → Claude / local, if configured
Why Groq is the default: free, fast, and has no billing-exhaustion failure mode the way a metered API does. If the active provider fails for any reason — rate limit, an outage, exhausted API credits — the next configured provider is retried automatically, and the response honestly reports whichever one actually answered rather than the one that was merely preferred. A single provider being down no longer means "Recommendation unavailable" as long as another configured provider is healthy.
